Vulnerability: Heap Buffer Overflow in smka_decode_frame (Smacker Audio Decoder)

=== SUMMARY ===

A heap buffer overflow exists in libavcodec/smacker.c:smka_decode_frame() when
processing a crafted Smacker audio packet with unp_size = 0. The initial
predictor sample values are written unconditionally to the output buffer without
first checking that nb_samples > 0, causing an out-of-bounds write of 1–4
attacker-controlled bytes past a zero-length (or minimally-padded) heap buffer.

Severity: HIGH (CWE-787: Out-of-bounds Write)

=== ROOT CAUSE ===

In smka_decode_frame() (smacker.c lines 591–749):

1. Line 611: unp_size = AV_RL32(buf) — attacker-controlled, set to 0.
2. Line 613: Check "unp_size > (1U<<24)" passes (0 is not > 16M).
3. Line 638: frame->nb_samples = 0 / (channels * (bits+1)) = 0.
4. Line 639: Check "unp_size % (channels * (bits+1))" = 0 % N = 0, passes.
5. Line 670: ff_get_buffer(avctx, frame, 0) allocates a buffer for 0 samples.
   On Linux/glibc, malloc(0) returns a valid pointer to a minimal allocation.
6. Lines 676–680 (16-bit path):
       for(i = stereo; i >= 0; i--)
           pred[i] = av_bswap16(get_bits(&gb, 16));  // reads attacker data
       for(i = 0; i <= stereo; i++)
           *samples++ = pred[i];   // *** WRITES PAST BUFFER ***

   This unconditionally writes (stereo + 1) int16_t values (2 or 4 bytes)
   to a buffer allocated for 0 samples.

7. Lines 721–724 (8-bit path):
       for(i = stereo; i >= 0; i--)
           pred[i] = get_bits(&gb, 8);
       for(i = 0; i <= stereo; i++)
           *samples8++ = pred[i];  // *** WRITES PAST BUFFER ***

   Same issue: writes (stereo + 1) bytes unconditionally.

The written values come directly from the bitstream (get_bits), meaning the
attacker controls the exact bytes written past the buffer.

=== IMPACT ===

- Stereo 16-bit: 4 bytes of attacker-controlled data written past the buffer.
- Mono 16-bit: 2 bytes of attacker-controlled data written past the buffer.
- Stereo 8-bit: 2 bytes of attacker-controlled data written past the buffer.
- Mono 8-bit: 1 byte of attacker-controlled data written past the buffer.

The overflow corrupts adjacent heap metadata or objects. With careful heap
layout manipulation (heap feng shui), this can potentially be exploited for
arbitrary code execution. At minimum, it causes heap corruption leading to
crashes (denial of service).

Note: ff_get_buffer may add AV_INPUT_BUFFER_PADDING_SIZE bytes of padding to
audio buffers, which can absorb small overwrites on some configurations. However,
this is implementation-dependent and not a reliable mitigation.

=== AFFECTED CODE ===

File: libavcodec/smacker.c
Function: smka_decode_frame (line 591)
Vulnerable lines: 676–680 (16-bit path), 721–724 (8-bit path)

=== SUGGESTED FIX ===

Add a check for unp_size == 0 after the existing validation:

    if (unp_size > (1U<<24)) {
        av_log(avctx, AV_LOG_ERROR, "packet is too big\n");
        return AVERROR_INVALIDDATA;
    }
+   if (unp_size == 0) {
+       av_log(avctx, AV_LOG_ERROR, "empty audio packet\n");
+       *got_frame_ptr = 0;
+       return avpkt->size;
+   }

Alternatively, check nb_samples > 0 before writing predictor values.
